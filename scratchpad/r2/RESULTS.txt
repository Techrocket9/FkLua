SIX RUNS OF THE DECISION LEG, on the same machine and the same afternoon:
  0.680  0.639  0.639  0.651  0.661  0.659      median 0.655, range 0.639-0.680

NOT ONE OF THE SIX REACHED THE 0.6 THRESHOLD. The rule was pre-registered
before the measurement, and it says: record the design, do not implement.

AND 0.655 IS AN UPPER BOUND ON THE WIN, because the prototype is generous to
the batch in three ways a real fk.batch_add could not be:

  - it carries NO PARENT COLUMN and writes NO HANDLES BACK, which a batch that
    builds a tree has to do;
  - it does not clear lastError, look the member up, mark and release the
    scratch region or encode a return block, all of which M.call_typed pays on
    every one of the fifty per-call elements;
  - its refusal semantics are absent entirely.

Adding the two things this harness cannot have moves the ratio the WRONG way
for the batch:

  the guest half.   A batch removes G-1 import calls and G-1 block
                    acquisitions. Credited generously with the whole measured
                    cost of a host call carrying no blocks (711 ns end to end,
                    internal/guest callcost probe 1, --persist=table) plus
                    ~200 ns for a 248-byte block, that is ~900 ns per element
                    for the per-call form and ~18 for the batch:
                    (6268 + 18) / (9510 + 900) = 0.604.

  the ENGINE.       add is a C++ GUI-element construction, which BOTH forms
                    pay once per element. r4b's own estimate from the audited
                    mods is 1.3-2.7 us. At 2 us:
                    (6268 + 18 + 2000) / (9510 + 900 + 2000) = 0.668.

  So the honest in-game figure is ~1.5x on a whole-window rebuild, against a
  rule that wanted 1.67x, and every correction that can be applied moves it
  toward 1.0 rather than away.

WHERE 4b's 12x WENT. It assumed five plain strings and interning ACROSS
refreshes. The audited row has five fields of which TWO are LocalisedStrings --
unions, so they are tier-2 slots inside the block and read_dyn walks them per
element in both forms -- and of the three poolable fields only `type` and
`style` repeat, because a GUI element's `name` is what a handler finds it by
and is distinct per element by construction. The pool over what is left is
worth 1.335x here, measured by ablation in the leg above.
